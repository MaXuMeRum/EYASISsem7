# Разбор `mt/mt_engine.py` — часть 1

Разберу первую часть `mt/mt_engine.py` — от модульного докстринга до `_load_nlp`.

## Модульный докстринг

```python
"""Система машинного перевода EN -> RU: прямой (пословный) и трансферный.

Трансферный режим реализован в три этапа, как предписывает методика:
анализ (дерево зависимостей EN) -> трансфер (листья дерева заменяются
русскими переводами, структура связей сохраняется) -> синтез
(линеаризация уже русского дерева в порядке слов, характерном для RU).
Русское дерево — самостоятельный артефакт, оно возвращается в результате
перевода в поле `russian_sentences`.
"""
```

**Что фиксирует докстринг.**

1. **Назначение модуля.** Машинный перевод EN→RU, два режима — прямой и трансферный.
2. **Соответствие методичке.** Три этапа трансферного перевода — **анализ → трансфер → синтез**. Это прямой референс к тексту ЛР: «Анализ и синтез независимы… связь между этапами обеспечивается введением особого этапа межъязыковых операций (собственно перевода, трансфера)».
3. **Архитектурное решение.** Русское дерево возвращается как **самостоятельный артефакт** — не побочный продукт, а часть результата (`russian_sentences`).

**Почему это важно.** Без докстринга читатель мог бы подумать, что трансферный перевод — «прямой + перестановка слов». С ним видно: это полноценный pipeline с тремя стадиями.

## Импорты

```python
import spacy
from collections import Counter

import pymorphy3

from core.translators import SyntaxTagTranslator
from mt.mt_constants import EN_STOPWORDS, SKIP_POS
from mt.synthetic_tree import SyntheticSentence, SyntheticToken
```

**Группы импортов.**

**1. Сторонние библиотеки:**

- `spacy` — морфология и синтаксис английского, парсинг текста.
- `pymorphy3` — морфология русского (POS, лемма, граммемы для русского дерева).

**2. Стандартная библиотека:**

- `Counter` из `collections` — счётчик частот для статистики.

**3. Внутренние модули:**

- `SyntaxTagTranslator` из `core.translators` — перевод тегов на русский.
- `EN_STOPWORDS`, `SKIP_POS` из `mt.mt_constants` — константы для фильтрации токенов.
- `SyntheticSentence`, `SyntheticToken` из `mt.synthetic_tree` — классы для построения русского дерева.

**Стиль группировки.** Стандартная библиотека (`Counter`) должна идти **первой группой** по PEP 8:

```python
from collections import Counter

import pymorphy3
import spacy

from core.translators import ...
```

Здесь `spacy` идёт первым, потом `Counter`, потом `pymorphy3`. Порядок смешан. Не критично, но правильнее было бы привести к единому стилю.

**Что бросается в глаза.**

- `Counter` импортируется из стандартной библиотеки, а не из `collections.abc` — правильно, это конкретный класс.
- `SyntaxTagTranslator` — единственный класс из `core`, используемый движком. Он отвечает за перевод тегов в UI-представление.

## `DEP_NORMALIZE` — нормализация зависимостей

```python
# en_core_web_sm размечен по UD v2, где часть связей называется иначе,
# чем в актуальной UD (dobj -> obj и т.д.). Русское дерево строим сразу
# в современных метках, чтобы дальше работали и линеаризация, и таблица.
DEP_NORMALIZE = {
    'nsubjpass': 'nsubj:pass',
    'auxpass': 'aux:pass',
    'dobj': 'obj',
    'pobj': 'obl',
    'prep': 'obl',
    'dative': 'iobj',
    'agent': 'obl:agent',
    'relcl': 'acl:relcl',
}
```

**Контекст (комментарий).** `en_core_web_sm` — модель spaCy, размеченная по **Universal Dependencies v2**, но с некоторыми устаревшими тегами. В более новой UD часть связей переименована. Комментарий объясняет, зачем нормализация: чтобы дальше в коде работать с современными метками.

**Что делает словарь.** Ключ — «устаревший/редкий» тег от spaCy. Значение — современный тег, к которому приводим.

**Разбор по парам.**

| Старое | Новое | Что означает |
|---|---|---|
| `nsubjpass` | `nsubj:pass` | Подлежащее пассивной конструкции |
| `auxpass` | `aux:pass` | Вспомогательный глагол пассива |
| `dobj` | `obj` | Прямое дополнение |
| `pobj` | `obl` | Объект предлога → обстоятельство |
| `prep` | `obl` | Предлог → обстоятельство |
| `dative` | `iobj` | Датив → косвенное дополнение |
| `agent` | `obl:agent` | Агент пассива |
| `relcl` | `acl:relcl` | Относительное придаточное |

**Почему `pobj` → `obl`, а не `iobj`.** Обсуждали раньше: `pobj` — объект предлога (`in the box`, `on the table`), в UD v2 это чаще `obl` (обстоятельство). Только часть случаев — `iobj` (косвенное дополнение в дативе). Твоё решение — всегда `obl` — консервативно, но безопасно.

**Где используется.** В `_build_russian_sentence`:

```python
dep=DEP_NORMALIZE.get(en_tok.dep_, en_tok.dep_ or ''),
```

Смысл: если `en_tok.dep_` в словаре — подставить новое значение; иначе оставить как есть. Дополнительно `or ''` защищает от `None` у spaCy-токенов.

**Что даёт нормализация.**

1. **Единообразие линеаризации.** `_LEFT_MODS` и `_RIGHT_MODS` используют только современные теги (`obj`, `obl`, `nsubj:pass`). Без нормализации пришлось бы дублировать: `('obj', 'dobj')`, `('obl', 'pobj', 'prep')` и т. д. — громоздко.
2. **Чистота русского дерева.** В `SyntheticToken.dep_` попадают только современные теги. Если кто-то смотрит на дерево, видит актуальный UD.
3. **Перевод в UI.** `SYNTAX_DEP_TRANSLATE` содержит оба варианта на всякий случай, но после нормализации переводится только современный.

**Минус.** Нормализация `pobj → obl` — упрощение. Реальный `pobj` может быть `iobj`. Потеря информации не критична для линеаризации (оба в `_RIGHT_MODS`), но для лингвистической точности — компромисс.

## Класс `MTEngine` — константы уровня класса

### `_LEFT_MODS` — модификаторы перед головой

```python
_LEFT_MODS = ('det', 'amod', 'nummod', 'nummod:entity', 'compound',
              'fixed', 'flat', 'poss', 'case', 'neg', 'expl',
              'aux', 'aux:pass', 'auxpass')
```

**Что это.** Кортеж типов зависимостей, которые в русском языке **идут перед** головным словом.

**Разбор.**

| Тег | Значение | Пример |
|---|---|---|
| `det` | Детерминатив | «этот парсер» |
| `amod` | Согласованное определение | «красивый дом» |
| `nummod` | Числительное-определение | «три книги» |
| `nummod:entity` | Числительное как именованная сущность | «пять яблок» |
| `compound` | Сложное слово | «компьютерный анализ» |
| `fixed` | Устойчивое выражение | «в течение» |
| `flat` | Плоская структура (имена) | «Иван Петров» |
| `poss` | Притяжательное | «мой дом» |
| `case` | Падежный маркер | предлог «в» |
| `neg` | Отрицание | «не» |
| `expl` | Формальное слово | «it» в «it rains» |
| `aux`, `aux:pass`, `auxpass` | Вспомогательные глаголы | «было написано» |

**Почему `aux` в левых.** В русском вспомогательный глагол часто идёт **перед** основным: «буду читать», «был написан». Поэтому `aux` — левый модификатор. Хотя с точки зрения синтеза это упрощение — русский не всегда ставит aux впереди.

**Почему кортеж, а не список.** Константа — не меняется. Кортеж неизменяем, чуть эффективнее по памяти. При `if dep in self._LEFT_MODS` разницы нет, но стилистически корректно.

**Почему приватное имя (`_`).** Не для внешнего использования. Внутренняя константа класса.

### `_RIGHT_MODS` — модификаторы после головы

```python
_RIGHT_MODS = ('nmod', 'appos', 'acl', 'acl:relcl', 'advmod', 'obl',
               'iobj', 'obj', 'dobj', 'pobj', 'ccomp', 'advcl', 'xcomp',
               'compound:prt', 'obl:agent', 'agent', 'conj', 'parataxis',
               'discourse', 'vocative', 'goeswith')
```

**Разбор.**

| Тег | Значение |
|---|---|
| `nmod` | Несогласованное определение (после головы) |
| `appos` | Приложение |
| `acl`, `acl:relcl` | Причастный оборот / относительное придаточное |
| `advmod` | Обстоятельство |
| `obl` | Обстоятельственный член |
| `iobj`, `obj` | Косвенное / прямое дополнение |
| `dobj`, `pobj` | Устаревшие варианты (на случай, если нормализация не сработала) |
| `ccomp`, `advcl`, `xcomp` | Придаточные разных типов |
| `compound:prt` | Частица фразового глагола |
| `obl:agent`, `agent` | Агент пассива |
| `conj` | Сочинённая связь |
| `parataxis` | Бессоюзная связь |
| `discourse`, `vocative` | Дискурсивные элементы, обращения |
| `goeswith` | Продолжение слова |

**Дублирование с современными метками.** В кортеже есть и `dobj`, и `obj`; и `pobj`, и `obl`; и `agent`, и `obl:agent`. Это **защита от неполной нормализации**: если `DEP_NORMALIZE` не сработал (тег не в словаре), оригинальный тег всё равно попадёт в правильную корзину.

**Почему так много.** `_RIGHT_MODS` — «приёмник» для всего, что не `_LEFT_MODS`. Задача — не потерять ни один токен. Если тег не в обоих множествах, он попадёт в fallback-проход `_linearize` по индексу, что даст неправильный порядок. Лучше включить побольше, чем упустить.

### `_SUBJECT_DEPS` — подлежащее

```python
_SUBJECT_DEPS = ('nsubj', 'nsubj:pass', 'nsubjpass', 'csubj')
```

**Что это.** Типы зависимостей, соответствующие подлежащему.

**Разбор.**

- `nsubj` — именное подлежащее (обычное).
- `nsubj:pass` — подлежащее пассивной конструкции.
- `nsubjpass` — устаревший тег того же.
- `csubj` — клаузальное подлежащее (придаточное в роли подлежащего).

**Где используется.** В `_linearize`:

```python
subjects = sorted((t for t in tokens if t.dep_ in self._SUBJECT_DEPS),
                  key=lambda x: x.i)
```

Подлежащие выносятся в начало предложения перед сказуемым — характерный русский порядок SVO.

### `_ADVERB_DEPS` — обстоятельство при корне

```python
_ADVERB_DEPS = ('advmod',)
```

**Кортеж из одного элемента.** Не строка, потому что используется в `in`-проверке. Если бы было `dep == self._ADVERB_DEPS` — можно было бы строку, но `dep in self._ADVERB_DEPS` работает и для кортежа, и для строки. Кортеж семантически правильнее: «список допустимых типов».

**Где используется.** В `_linearize`:

```python
adverbs = sorted((t for t in tokens
                  if t.dep_ in self._ADVERB_DEPS and t.head is root),
                 key=lambda x: x.i)
```

**Только `advmod` при root.** Обстоятельства при других словах не выносятся — они остаются как модификаторы своих голов. Логика: «Он быстро читает» — «быстро» при глаголе, выносится перед сказуемым.

## `__init__`

```python
def __init__(self, dict_manager):
    self.dict_manager = dict_manager
    self.tag_translator = SyntaxTagTranslator()
    self._nlp = None
    self._morph_ru = pymorphy3.MorphAnalyzer(lang='ru')
```

**`self.dict_manager = dict_manager`** — внедрение зависимости (Dependency Injection). `MTEngine` не создаёт словарь сам, а **принимает** его в конструкторе. Плюсы:

- тестирование: можно передать mock.
- контроль жизненного цикла: `DictionaryManager` создаётся один раз в `App`, используется всеми движками.
- нет циклических импортов: `MTEngine` не знает, откуда приходит `dict_manager`.

**`self.tag_translator = SyntaxTagTranslator()`** — переводчик тегов для статистики и UI. Создаётся один раз на экземпляр. Дёшево, но `SyntaxTagTranslator` — stateless, мог бы быть общим для всех.

**`self._nlp = None`** — флаг ленивой загрузки spaCy-модели. Модель загрузится при первом переводе через `_load_nlp()`. Экономия:

- если пользователь открыл UI, но не переводил — модель не загружается (экономия 50+ МБ RAM).
- если модель уже загружена другим экземпляром — свой экземпляр её не перегружает.

**`self._morph_ru = pymorphy3.MorphAnalyzer(lang='ru')`** — анализатор русской морфологии. В отличие от spaCy, **создаётся сразу** в конструкторе.

**Почему по-разному.** pymorphy3 грузит словарь (~5 МБ), но это быстрее, чем spaCy-модель. И `_morph_ru` используется в `_build_russian_sentence`, который вызывается в **любом** режиме перевода (и прямой, и трансферный тоже строит русское дерево). Значит, без него не обойтись — грузить сразу логично.

## `_load_nlp` — ленивая загрузка spaCy

```python
def _load_nlp(self):
    if self._nlp is None:
        try:
            self._nlp = spacy.load("en_core_web_sm")
        except OSError:
            raise RuntimeError(
                "Модель spaCy 'en_core_web_sm' не установлена. "
                "Выполните: python -m spacy download en_core_web_sm"
            )
    return self._nlp
```

**Логика.**

1. **Быстрый выход.** Если модель уже загружена — вернуть её.
2. **Ленивая загрузка.** `spacy.load(...)` — тяжёлая операция (0.5–3 секунды, память). Первый вызов перевода её оплатит, последующие — нет.
3. **Обработка ошибки.** `except OSError` — то, что бросает `spacy.load`, если модель не установлена.
4. **Человекочитаемое сообщение.** Вместо `OSError: [E050] Can't find model 'en_core_web_sm'` — «Модель не установлена. Выполните: python -m spacy download en_core_web_sm». Пользователь сразу знает, что делать.
5. **Проброс исключения.** `RuntimeError` уходит наверх. Ловится в `translate_direct` и `translate_transfer` (в UI-обёртке `App._render_translation_tab` — `except RuntimeError as e: st.error(str(e))`).

**Жёсткое имя модели.** `"en_core_web_sm"` захардкожено. В отличие от `SyntaxAnalyzer`, где есть `SPACY_MODELS = {...}` — словарь для двух языков.

**Почему не вынести в константу.** Движок работает только с английским (переводит с EN). Одна модель. Менять нечего. Заводить константу `_MODEL_NAME = "en_core_web_sm"` было бы избыточно.

**Кэширование на уровне экземпляра.** `self._nlp` — кэш на конкретный `MTEngine`. Если создать второй `MTEngine` — модель загрузится заново. Но в приложении один `MTEngine` на всё время работы.

## Что можно было бы улучшить (первая часть)

1. **Порядок импортов** по PEP 8: стандартная библиотека первой.
2. **`except OSError`** расширить до `(OSError, ImportError)` — редкий, но реальный кейс поломанной установки.
3. **Дублирование `nsubjpass`/`nsubj:pass`** в `_SUBJECT_DEPS`: если нормализация работает, второй тег не нужен. Но как защита — оправдано.
4. **`_ADVERB_DEPS` как кортеж из одного элемента** — мог бы быть просто строкой, но кортеж семантически чище.
5. **`DEP_NORMALIZE['pobj'] = 'obl'`** — упрощение, о котором стоит упомянуть в отчёте.

## Итог

Первая часть файла — «настройка»: константы, определяющие **как** движок будет работать, и ленивая инициализация тяжёлых ресурсов.

- **Модульный докстринг** фиксирует три роли (прямой/трансферный/русское дерево) и соответствие методичке.
- **`DEP_NORMALIZE`** приводит старые теги UD к современным — единообразие для линеаризации.
- **`_LEFT_MODS` / `_RIGHT_MODS`** — правила порядка слов: что перед головой, что после.
- **`_SUBJECT_DEPS` / `_ADVERB_DEPS`** — что выносится вперёд при линеаризации.
- **`__init__`** — DI для словаря, ленивая инициализация spaCy, сразу — pymorphy3.
- **`_load_nlp`** — ленивая загрузка с понятной ошибкой.

Всё это работает, ничего лишнего. Основные замечания — косметические (порядок импортов, широта `except`).
